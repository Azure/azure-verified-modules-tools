The limit is enforced server-side at the last step of the pipeline, so it costs a whole release to discover and leaves a tag and a Release pointing at a version that was never published. `Get-AvmReleaseNotes.ps1` gained `-MaxLength`, which truncates on a line boundary from the *bottom* — a section leads with `### Breaking`, so the tail is the safe end to lose — and appends a link to the GitHub Release, which has no such limit and still carries the full notes. Newlines are measured at their CRLF worst case because the packer may rewrite them on the way into the nuspec. The important half is the second guard: the `build` task re-reads the stamped manifest with `Import-PowerShellDataFile` and fails if the value is still over, so the cap is verified against what actually ships rather than trusted from the generator — which is the same principle as F48's `namespaces seen` and is what caught a mutation that disabled the cap silently. A repo-wide test also asserts every released CHANGELOG section fits, so a future section that outgrows the limit fails in `pre-commit` rather than after the tag. Tracked as **F49**.

## Known issues / active blockers

- _(2026-08-06)_ **`pwsh -File` splits `-flag=value` arguments at the first `=` or `:`, so Component-tier stub binaries must never match on `=`-joined flags.** The Component tier puts stub binaries on `PATH` via a `.cmd` shim that calls `pwsh -NoProfile -ExecutionPolicy Bypass -File "<stub>" %*`. That parameter parser treats `=` and `:` as argument separators, so `--config=Q:\repo\avm.tflint.hcl` reaches the stub as the **two** arguments `--config=Q` and `\repo\avm.tflint.hcl`. It is `pwsh -File` itself, not `cmd.exe` — a direct PowerShell-to-pwsh call mangles it identically. Empirically rejected workarounds: cmd-level re-quoting via a `shift` loop (still splits; explicit quotes leak literal `"` into `$args`), the `--%` stop-parsing token, and a bare `--` separator. **Space-separated tokens survive intact**, so engines should pass path-bearing values as `--flag <value>` (which `Invoke-AvmTerraformDocs` already did; `Invoke-AvmTerraformLint` was brought into line on 2026-08-06). Production code is unaffected because `Invoke-AvmProcess` builds argv through `ProcessStartInfo.ArgumentList` and never routes through a shell — this is a **test-harness-only** artefact. The failure mode is silent: the old tflint stub only checked `$args -contains '--recursive'`, so `--format=json` had been splitting all along without anyone noticing. Documented on `tests/helpers/Install-AvmStubLauncher.ps1`. _(Related, now closed)_ `./build.ps1 pre-commit` used to run layout + lint + the **Unit tier only**, while `ci` additionally runs `component` — so a green local gate did not predict a green CI run, which is exactly how the broken stub contract reached CI. `component` is now part of `pre-commit` (~30s); `coverage` and `integration` remain CI-only.

- _(2026-08-06)_ **`./build.ps1 integration` is not reliably runnable on a Windows dev box; treat CI as the source of truth for that tier.** Two independent local-only failure modes were hit while validating the `check policy` fix, both of which abort the chain at `transform` and look like product defects but are not. (1) **Windows Defender quarantines the freshly-downloaded `mapotf.exe`** — `Invoke-AvmProcess` surfaces it as `Failed to start '<AVM_HOME>\tools\mapotf\0.1.4\mapotf.exe': … Operation did not complete successfully because the file contains a virus or potentially unwanted software.` It is a heuristic hit on an unsigned Go binary in a temp-rooted `AVM_HOME`, is non-deterministic (the first run of a fresh download often succeeds before the scan lands, which is why one test passes and later ones fail fast), and does not occur on GitHub runners. (2) **A `terraform` on `PATH` breaks `mapotf transform`** (previously documented): the WinGet shim at `%LOCALAPPDATA%\Microsoft\WinGet\Links\terraform.exe` is enough to trigger it; strip that directory from `$env:PATH` for the run. Neither reproduces in CI, so diagnose integration failures from the workflow logs (`gh run view <id> --job <jobId> --log`, noting logs are unavailable while a run is in progress) rather than from a local run. To validate a single step without the mapotf dependency, call the engine directly — e.g. `Invoke-AvmCheckPolicy -Path <fixture> -Ecosystem terraform` — which exercises the real binaries without going through `transform`.

 `src/Avm.Authoring/Engines/ManagedFiles/Sync-AvmManagedFile.ps1` is a reduced reimplementation of `tf-repo-mgmt/scripts/lib/{ManagedFiles,RepositoryConfig}.ps1`. `avm pr-check` opens with `Invoke-AvmSync -CheckDrift`, which hard-fails on any difference between what this module computes and what the governance pipeline actually wrote — so **any behavioural divergence surfaces as permanent, unfixable false drift on every module repo**, not as a local test failure. Two divergences were found and closed on 2026-07-31 (stacked overlays; `.gitkeep` filtering), both only reachable once a repo belonged to an overlay group, which is why they went unnoticed. There is **no automated parity gate** between the two repos. When `tf-repo-mgmt` changes its resolution or file-enumeration semantics, this engine must be updated in lockstep, and a governance change should not merge before a `Avm.Authoring` release carrying the matching fix reaches PSGallery. Verification recipe: resolve a repo id against a real `config.json` + `managed-files` checkout with both implementations and compare the **file counts and per-path sources**, not just the overlay list. _(2026-07-31, follow-up)_ Overlay precedence is now **explicit** rather than positional: each `repositoryGroups` entry may carry an integer `managedFilesOrder` (default `0`), overlays sort by that value ascending with ties broken by declaration order, and a lower order is applied earlier and therefore loses. Previously precedence derived purely from array order in `config.json`, so alphabetising the file would have silently flipped it. The sort is an explicit `(Order, Index)` tuple rather than a stable sort, so it is deterministic irrespective of `Sort-Object` stability. Governance carries the identical change in the same PR.

**Option A — Build-and-host pattern.** A new CI workflow in this repo (or a sibling release-only repo) cross-compiles `avmfix` / `mapotf` / `grept` from their upstream tags for 6 platforms, signs + checksums, and publishes as GitHub Releases under `Azure/*`. `tools.lock.psd1` entries pin to those URLs + SHA256s. - **Pros**: install model unchanged; trustworthy provenance; deterministic install (offline-cacheable, SHA-verifiable, lock-pinned).
- **Cons**: ongoing release pipeline maintenance; must track each upstream tag; need agreement with upstream maintainers (or accept "soft fork" with our own release cadence); new GitHub Actions surface.
- **Effort**: one new workflow, one new lock entry per tool, ~2 sub-slices per tool (CI + lock).

**Option B — Native `go install` path in `Install-AvmTool`.** Add a `goModule` lock entry shape (`module`, `version`, `entrypoint`) that runs `go install <module>@<version>` into the managed cache, then resolves the resulting binary. `Resolve-AvmTool` learns a second install kind.

- **Cons**: introduces a **Go-toolchain prerequisite** (`go` must be on `$PATH` at install time, both locally and in CI); deterministic install model weakens (no SHA verification of the built binary against a known-good hash — supply-chain integrity relies on Go module proxy + `sum.golang.org` checksum DB); spec §10 currently assumes URL-downloadable archives, so it would need an explicit amendment.
- **Effort**: one new lock-entry kind, one new install branch in `Install-AvmTool`, doctor-step extension to check for `go` on `$PATH`, spec §10 amendment.

- **Cons**: doesn't deliver on Phase 2's "no container required" promise for those three steps; pushes the call to Phase 3+.
