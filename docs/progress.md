The PSGallery push moved with it rather than staying behind: signing has to happen before the push, and the Gallery accepts a version exactly once, so leaving `.github/workflows/release.yml` in place would let an unsigned build win the race — hence the workflow is **deleted**, not disabled. The pipeline checks this repo out at the release tag, stages and stamps the module with the same `Get-AvmReleaseNotes.ps1` / `Set-AvmModuleVersion.ps1` scripts CI already uses (so the 10600-char F49 cap still applies), signs with `signing_profile: external_distribution` — one task per extension rather than one `;`-separated glob, because the separator is documented but unexercised here — then **verifies**: whether ESRP fails or silently succeeds when its file filter matches nothing is unverified, so `Test-AvmAuthoringSignature.ps1` re-reads every staged file and fails the build listing any that lack a signature block. That gate is load-bearing because the pipeline uses the Linux pool (`featureFlags.linuxEsrpSigning: true`) for mapotf parity, and while OneBranch documents `.ps1` as supported cross-platform it does not list `.psm1`/`.psd1`; the fallback is a Windows pool, as `PowerShell/PSResourceGet` uses. Publishing is gated by a single `dryRun` boolean (default off), matching mapotf — both publish legs are idempotent, so the earlier cumulative `releaseAction` ladder only added ways to leave a release half-finished. **The GitHub Release is authored by hand before the run**, as a *published pre-release* carrying the tag and the notes: publishing is what creates the tag, a draft release does not create one, and the pipeline checks the tag out. The pipeline never creates a release and never writes a body, it only edits an existing one — the same shape mapotf adopted in [ADO PR 2276](https://dev.azure.com/github-private/azure/_git/Azure-Verified-Modules/pullrequest/2276) and redesigned in [ADO PR 2278](https://dev.azure.com/github-private/azure/_git/Azure-Verified-Modules/pullrequest/2278), mirrored here by [ADO PR 2279](https://dev.azure.com/github-private/azure/_git/Azure-Verified-Modules/pullrequest/2279). Two edits, not one, because `GitHubRelease@1` PATCHes *before* it uploads assets, so a single promoting edit would present the release as finished while the archives were still going up; the first edit forces `isPreRelease` back on — which recovers an accidentally promoted release, and means a re-run against a finished one still produces the promotion — and uploads, the last promotes with `makeLatest: legacy` so a hotfix cut against an older line cannot displace a newer release. The upload deliberately runs **before** the gallery push and the promotion **after** it, so a missing release fails the run while nothing has been published — a gallery version cannot be withdrawn — and the release stops being a pre-release only once the module is installable. Verified locally end-to-end at `v0.1.8` against a simulated signature: 93/93 files staged and stamped, verification correctly fails unsigned and passes signed, the zip is byte-identical in shape to the old workflow's, and a signed `.psd1` still passes `Test-ModuleManifest` and imports. **Provisioned**: variable group `Azure-Verified-Modules-Tools` (ADO id 35) now holds the `powerShellGalleryApiKey` secret, deliberately separate from the shared `Azure-Verified-Modules` group so the key is reachable only from this pipeline. **Blocked on**, in order: creating the pipeline definition, now unblocked because the YAML is on `main` — mirror `Azure-Verified-Modules-Release-Mapotf` (id 1203): folder `\OneBranch\Azure-Verified-Modules`, repo `Azure-Verified-Modules`, branch `refs/heads/main`, yaml `.pipelines/release-avm-authoring.yml`; authorising the variable group for that new definition; then a first run with `dryRun` ticked. The Production Readiness Check pauses **indefinitely** until a human approves, and approvals cache per **commit**, not per pipeline — so a topic-branch run has no PR, no Proof of Presence and no approvers and always pauses, meaning this can only be exercised from `main` after a compliant PR merges (mapotf took seven PRs). Re-queuing an already-approved commit does not pause again, so sweep `dryRun` and `version` against one merge. Still unconfirmed: whether PSGallery is reachable from the isolated OneBranch container, and whether `external_distribution` accepts `.psm1`/`.psd1` — the per-file record exists only in the published `drop_<stage>_<job>_signingLogs1` artifact, never the task log, which only prints a file count.

## Known issues / active blockers

Resolved entries are in [`progress-archive.md`](progress-archive.md#resolved-issues-and-blockers).

- _(2026-08-06)_ **`pwsh -File` splits `-flag=value` arguments at the first `=` or `:`, so Component-tier stub binaries must never match on `=`-joined flags.** The Component tier puts stub binaries on `PATH` via a `.cmd` shim that calls `pwsh -NoProfile -ExecutionPolicy Bypass -File "<stub>" %*`. That parameter parser treats `=` and `:` as argument separators, so `--config=Q:\repo\avm.tflint.hcl` reaches the stub as the **two** arguments `--config=Q` and `\repo\avm.tflint.hcl`. It is `pwsh -File` itself, not `cmd.exe` — a direct PowerShell-to-pwsh call mangles it identically. Empirically rejected workarounds: cmd-level re-quoting via a `shift` loop (still splits; explicit quotes leak literal `"` into `$args`), the `--%` stop-parsing token, and a bare `--` separator. **Space-separated tokens survive intact**, so engines should pass path-bearing values as `--flag <value>` (which `Invoke-AvmTerraformDocs` already did; `Invoke-AvmTerraformLint` was brought into line on 2026-08-06). Production code is unaffected because `Invoke-AvmProcess` builds argv through `ProcessStartInfo.ArgumentList` and never routes through a shell — this is a **test-harness-only** artefact. The failure mode is silent: the old tflint stub only checked `$args -contains '--recursive'`, so `--format=json` had been splitting all along without anyone noticing. Documented on `tests/helpers/Install-AvmStubLauncher.ps1`. _(Related, now closed)_ `./build.ps1 pre-commit` used to run layout + lint + the **Unit tier only**, while `ci` additionally runs `component` — so a green local gate did not predict a green CI run, which is exactly how the broken stub contract reached CI. `component` is now part of `pre-commit` (~30s); `coverage` and `integration` remain CI-only.

- _(2026-08-06)_ **`./build.ps1 integration` is not reliably runnable on a Windows dev box; treat CI as the source of truth for that tier.** Two independent local-only failure modes were hit while validating the `check policy` fix, both of which abort the chain at `transform` and look like product defects but are not. (1) **Windows Defender quarantines the freshly-downloaded `mapotf.exe`** — `Invoke-AvmProcess` surfaces it as `Failed to start '<AVM_HOME>\tools\mapotf\0.1.4\mapotf.exe': … Operation did not complete successfully because the file contains a virus or potentially unwanted software.` It is a heuristic hit on an unsigned Go binary in a temp-rooted `AVM_HOME`, is non-deterministic (the first run of a fresh download often succeeds before the scan lands, which is why one test passes and later ones fail fast), and does not occur on GitHub runners. (2) **A `terraform` on `PATH` breaks `mapotf transform`** (previously documented): the WinGet shim at `%LOCALAPPDATA%\Microsoft\WinGet\Links\terraform.exe` is enough to trigger it; strip that directory from `$env:PATH` for the run. Neither reproduces in CI, so diagnose integration failures from the workflow logs (`gh run view <id> --job <jobId> --log`, noting logs are unavailable while a run is in progress) rather than from a local run. To validate a single step without the mapotf dependency, call the engine directly — e.g. `Invoke-AvmCheckPolicy -Path <fixture> -Ecosystem terraform` — which exercises the real binaries without going through `transform`.

- _(2026-07-29)_ **`mapotf transform` fails on any machine that already has a `terraform` on `PATH`.** `Invoke-AvmTerraformTransform.ps1` prepends the AVM-pinned terraform directory to `PATH` for the mapotf subprocess, but mapotf resolves *every* `terraform` match on `PATH` and then execs the newline-joined concatenation, so a second install (e.g. the WinGet shim at `…\WinGet\Links\terraform.exe`) yields `fork/exec <pinned>\terraform.exe⏎<winget>\terraform.exe: The filename, directory name, or volume label syntax is incorrect.` and `avm pre-commit` / `avm pr-check` die at the `transform` step. Not a regression — `git diff origin/main...HEAD` is empty for that engine — and invisible on CI because GitHub runners ship no terraform on `PATH`, but it will hit most Windows developers. `mapotf transform --help` exposes no terraform-path flag, so the only lever is PATH surgery (drop every `PATH` entry containing a terraform executable, then prepend the pinned dir), which is risky on Linux/macOS where terraform commonly shares `/usr/local/bin` with other required binaries. Needs a separate, deliberately-scoped fix; the local workaround is to strip the offending directory from `PATH` for the run.

- _(Mitigated 2026-05-20)_ `Invoke-ScriptAnalyzer` occasionally throws `NullReferenceException` from inside its own rule pipeline (no file/line in our code named). Observed on both `windows-latest` (run 26156193662, commit `bd778fd`) and `ubuntu-latest` (run 26156731288, commit `dc5b7f0`); re-run of the same commit always passes. Cause: a transient race in PSSA's rule-discovery / settings-hydration path. Mitigation: `build/avm.build.ps1` now wraps `Invoke-ScriptAnalyzer` in `script:Invoke-ScriptAnalyzerWithRetry`, which retries up to `AVM_LINT_MAX_ATTEMPTS` (default 3) times when, and only when, the caught exception (or any `InnerException`) is a `NullReferenceException` or carries the `Object reference not set to an instance of an object` message. Real findings come back as `DiagnosticRecord` objects and never trigger a retry. Each retry emits a `Write-Warning` so flakes remain visible in build logs. **2026-07-29:** still live, and it can exhaust the default 3 attempts — six consecutive failures were observed locally on one commit. Bisecting per file confirmed it is *not* file-specific: a full recursive run named `Format-AvmBicepModule.ps1` and `Invoke-AvmTerraformCheckPolicy.ps1`, but neither reproduces in isolation (3/3 clean each) and both are untouched by the branch. Raising `AVM_LINT_MAX_ATTEMPTS` (10 worked) is the escape hatch when a plain re-run keeps losing the race. **2026-07-31:** PR #13 exhausted all 3 attempts on `windows-latest` in ~10s while `ubuntu-latest` and `macos-latest` passed the identical commit, and a local `pre-commit` run needed 3 attempts — so the per-attempt failure rate is high enough that 3 is not a safe ceiling. The default is now **8** with escalating backoff (`500ms * attempt`); the `AVM_LINT_MAX_ATTEMPTS` override still applies. Note the invocation combines `-CustomRulePath` + `-RecurseCustomRulePath` with a recursive `-Path`, which is the documented upstream trigger for this NRE; splitting built-in from custom-rule analysis is the candidate real fix if retries ever stop being enough.

- _(2026-07-31)_ **The managed-files engine is a reimplementation of governance, with no automated parity gate.** `src/Avm.Authoring/Engines/ManagedFiles/Sync-AvmManagedFile.ps1` is a reduced reimplementation of `tf-repo-mgmt/scripts/lib/{ManagedFiles,RepositoryConfig}.ps1`. `avm pr-check` opens with `Invoke-AvmSync -CheckDrift`, which hard-fails on any difference between what this module computes and what the governance pipeline actually wrote — so **any behavioural divergence surfaces as permanent, unfixable false drift on every module repo**, not as a local test failure. Two divergences were found and closed on 2026-07-31 (stacked overlays; `.gitkeep` filtering), both only reachable once a repo belonged to an overlay group, which is why they went unnoticed. There is **no automated parity gate** between the two repos. When `tf-repo-mgmt` changes its resolution or file-enumeration semantics, this engine must be updated in lockstep, and a governance change should not merge before a `Avm.Authoring` release carrying the matching fix reaches PSGallery. Verification recipe: resolve a repo id against a real `config.json` + `managed-files` checkout with both implementations and compare the **file counts and per-path sources**, not just the overlay list. _(2026-07-31, follow-up)_ Overlay precedence is now **explicit** rather than positional: each `repositoryGroups` entry may carry an integer `managedFilesOrder` (default `0`), overlays sort by that value ascending with ties broken by declaration order, and a lower order is applied earlier and therefore loses. Previously precedence derived purely from array order in `config.json`, so alphabetising the file would have silently flipped it. The sort is an explicit `(Order, Index)` tuple rather than a stable sort, so it is deterministic irrespective of `Sort-Object` stability. Governance carries the identical change in the same PR.

## Pivots / direction changes

- _(2026-05-27)_ **Phase 2 §2 supply-chain audit surfaces a blocker.** Investigating the next implementation slice (`avm format`-`avmfix`-chain) discovered that 3 of the 4 Go tools needed for Phase 2 §2 — `avmfix`, `mapotf`, `grept` — ship **no GitHub binary releases**, only Go source via `go install`. Only `conftest` ships proper 6-platform releases. The existing `tools.lock.psd1` schema (`urlTemplate` + per-platform SHA256s) cannot describe a `go install` tool without either (a) standing up our own build-and-host CI pipeline or (b) adding a new `goModule` install kind to `Resolve-AvmTool` / `Install-AvmTool`. The consolidation plan flagged this risk at §11 open question 2 but did not resolve it. **No code slice is started — this turn documents the audit and the three-option decision matrix** in the new **Phase 2 §2 supply-chain audit** sub-section under Phase 2 below, plus a corresponding **Known issues** entry. The user needs to pick a resolution path (A: build-and-host / B: `go install` / C: defer §2 entirely) before any of the four engine-implementation slices can start; `avm check policy` (conftest) and the pinned-asset feature can proceed in parallel.

- _(2026-05-26)_ **Bicep docs walker reverted; Terraform `pre-commit` / `pr-check` prioritised.** The slices 1-4f ARM-JSON walker that landed between 2026-05-21 and 2026-05-22 (`Convert-AvmBicepToArm` -> `Get-AvmArmResource` / `Get-AvmArmParameter` / `Get-AvmArmParameterDetail` -> `Format-AvmBicep*Section` -> `Merge-AvmReadmeSection`, plus `Invoke-AvmBicepDocs` as the in-process glue) has been removed from the tree. Reason: the work is going to be redesigned as a **separate, focused CLI command** rather than an in-process engine reachable through `avm docs`; carrying the spike forward risks two divergent implementations. `Invoke-AvmBicepDocs` is now a small stub that throws `AvmConfigurationException`, which `Invoke-AvmPreCommit` and `Invoke-AvmPrCheck` already report as `Status='skipped'` — the verb chain stays green. The 9 walker source files + 9 walker test files were `git rm`-d in the same commit; the prior implementation lives on commit `17f63cf` if its diff is ever useful as reference. Highest priority on the new plan: validating the **Terraform `pre-commit` and `pr-check` compositions** end-to-end via Pester (smoke-style, using stub binaries under `tests/fixtures/bin/`). That's the primary way contributors will actually run `avm`, and it has been stalled behind the Bicep work for too long. Phase 2 §"deliverables not started" is reordered below to put `pre-commit` / `pr-check` first, followed by the engine-implementation unblockers (`transform` -> `mapotf`, `check policy` -> `conftest`, `check convention` -> `grept`, `format` enhancement -> `avmfix`). The new Bicep docs CLI command stays intentionally undesigned until Phase 2 is closing out.

## Host-language reviews

- _(2026-05-20)_ Re-confirmed mid-Phase 1 (after the Bicep docs walker slice 1 shipped). Conclusion: **stay on PowerShell, no Option 3 trigger has fired.** Friction observed this turn — strict-mode 3.0 quirks (`.PSObject.Properties.Name` on empty pscustomobjects, `$arr[-1]` ambiguity, inline-if `@()` vs `@($x)` type-mixing), Pester `<word>` placeholder trap in `It` titles, backtick literalness in single-quoted regex — was all *language quirks*, not *language fit*. Solved once per pattern and codified (use `[List[string]]::new()` + explicit `[$list.Count - 1]` indexing; use `.PSObject.Properties['name']` indexer instead of `.Name` projection; rename `It` titles that contain `<word>` substrings; count backticks in single-quoted regex literally). The Bicep walker we just shipped is three in-process function calls (`Convert-AvmBicepToArm` → `Format-AvmBicepOutputsSection` → `Merge-AvmReadmeSection`); in C# every one of those would be a `pwsh.exe` shell-out or a `Microsoft.PowerShell.SDK` runspace. None of the documented Option-3 triggers (argv parser ≥2×, polished TUI, startup latency dominates, Windows SIGINT blocker, concurrency runspaces can't service) have fired. Next reconsideration point flagged: the recursive UDT walker in the upcoming Parameters-section slice — if discriminated-union or `$ref` cycle handling gets error-prone, that's where weak typing will start to hurt.
