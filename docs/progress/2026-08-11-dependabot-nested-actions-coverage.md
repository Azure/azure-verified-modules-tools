## Outcome

Extend the repository Dependabot configuration so the SHA-pinned actions that
live outside the root `.github/workflows` directory are kept up to date. This
makes the "GitHub Actions dependencies are managed centrally" decision recorded
in `docs/progress/2026-08-11-managed-dependabot-actions.md` actually hold.

Dependabot does not recurse for the `github-actions` ecosystem. With
`directory: /` it fetches only root `.github/workflows/*.y{a,}ml` plus a root
`action.yml`/`action.yaml`. For any non-root directory it fetches
`*.y{a,}ml` directly inside that directory and does not descend further. Two
sets of pins were therefore unmonitored:

| Path | Pinned `uses:` |
| --- | --- |
| `repository-management/managed-files/files/root/.github/workflows/` | 44 |
| `repository-management/repository-sync/actions/avm-repos/action.yml` | 2 |

Globs are supported by `directories` but not by `directory`, so the managed
files entry is written as `files/*/.github/workflows`. That currently resolves
to the `root` flavour only, and picks up `canary` and `canary-tooling`
automatically when those placeholders gain workflows.

## Blockers or dependencies

`repository-management/managed-files/files/root/.github/workflows/issue-triage.lock.yml`
is generated by `gh aw compile` and carries a `DO NOT EDIT` banner. Dependabot
cannot exclude a single file from a directory, so it will raise pull requests
against that lock file. Those edits are reverted the next time the workflow is
recompiled from `issue-triage.md`. No CI check currently verifies the lock is
in sync, so this is churn rather than breakage.

Follow-up, out of scope here:
`repository-management/managed-files/files/root/.github/workflows/pr-check.yml`
calls `Azure/azure-verified-modules-tools/.github/workflows/terraform-module.yml@main`.
A floating branch ref is not covered by Dependabot and conflicts with the SHA
pinning stance in `docs/avm-implementation-spec.md`.
